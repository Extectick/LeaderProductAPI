# Контекст чата Help

Реализация от 5 ноября 2026. Провайдер остаётся direct OpenAI, модель
`gpt-6.1-sol`, reasoning `medium`. Контекст принадлежит конкретному обращению
и его владельцу. История другого обращения автоматически не подмешивается.

## Что заимствовано из T3 Code

Референс: локальный исходный код T3 Code, commit `9e855385`.
CodexAdapterV2 начинает/возобновляет provider thread и вызывает native compaction;
повторяет дополнительные инструкции после сжатия. HandoffBudget сохраняет целые
сообщения по приоритетам и явно отмечает пропуски. OrchestratorMcpService даёт
постраничное чтение истории, включая продолжение большого сообщения.

В Help используются эти принципы, адаптированные к собственному Responses
adapter. Это семантическая JSON-сводка приложения со ссылками на сообщения,
а не копия Codex thread или encrypted `/responses/compact`. T3 организует
инструкции, контекст и инструменты; он не обучает модель на диалоге автоматически.

## Хранение и сбор контекста

Оригиналы остаются в `HelpMessage` и приватном S3. Они не заменяются сводкой.
`loadHelpConversation` выбирает последние 400 допустимых сообщений и первое
сообщение владельца, без обрезания каждого текста. Это ограничение подготовки
одного запроса, а не глубины сохранённой истории: старые оригиналы доступны
через инструменты чтения/поиска.

`prepareHelpConversationWindow` держит окно 96 КиБ сериализованного JSON.
При превышении 64 КиБ обновляет сводку старой части, сохраняя свежий хвост
около 24 КиБ. Вход одного сжатия ограничен 128 КиБ; сообщения сохраняются целиком.
Покрытие, пропуски и доступность сжатия передаются модели явно. Если сжатие
недоступно, поиск по оригиналам продолжает работать; отмена и потеря прав
завершают обработку.

Сводка содержит цель, условия, решения, ранее сообщавшиеся результаты и открытые
вопросы, с `messageIds` для каждого пункта. Исправление сотрудника важнее старого
значения. Смена темы обновляет цель. Пересказ ассистента не становится
подтверждением слов сотрудника или действующих прав/данных 1С.

Сжатие выполняет та же настроенная модель/effort через тот же VPN и серверный
ключ, с `store:false`, строгой схемой и без инструментов. Сводка не содержит
внутренние рассуждения и не превращается в системные инструкции.

Кэш лежит только в приватном `HelpAssistantJob.context.helpContextSummary`;
оригинальные `inputs` сохраняются в том же envelope. Он фиксируется вместе с
финальным ответом в существующей fenced-транзакции после успешного lease/CAS.
Новый процесс восстанавливает валидный кэш из БД. Миграция не нужна.

## Поиск и файлы

Три инструмента навсегда связаны с owner/ticket/sequence текущего запуска:

- `help_search_history`: буквальный поиск, до 10 результатов, экранирование SQL
  wildcard; возвращает источники и признак следующей страницы.
- `help_read_history`: до 20 сообщений, ID/sequence/role, продолжение через
  `messageId` и `offset`; один текстовый фрагмент до 8000 символов, суммарно
  до 16000. ID другого обращения не читается даже администратором.
- `help_read_attachment`: только собственное вложение допустимого сообщения.
  TXT/MD/CSV/JSON до 256 КиБ; PDF/DOCX до 2 МиБ, через изолированный extractor.
  Проверяются тип, размер, SHA-256 и привязка после I/O. Страницы до 8000 символов.
  Сканированный PDF требует OCR; неподдерживаемый формат явно отмечается.

Изображение, найденное по старому сообщению, можно передать на vision-анализ:
до двух за запуск, до 5 МиБ исходник, ограниченный очищенный JPEG. Bytes живут
только в текущем provider input, не в сводке или публичной activity.
Имя файла само по себе никогда не означает, что содержимое прочитано.

Перед ответом о раннем выборе при неполном покрытии модель должна восстановить
оригиналы через историю. Восстановленная история не заменяет свежий запрос 1С:
актуальные бизнес-данные требуют личного подключения и новых tool proofs.
Корпоративные инструкции по-прежнему требуют разрешённых источников.

## Границы и проверки

Fingerprint охватывает допустимые сообщения, текст, роли, редактирования и
метаданные/хеши вложений до зафиксированного sequence. Изменение оригинала
сбрасывает сводку. Права, состояние обращения и fingerprint проверяются до и
после внешнего сжатия, перед запросами модели и при финальном сохранении.
Остановка, передача в IT и смена владельца не должны опубликовать старый ответ.
Автоматическая подготовка изображений и employeeContext используют тот же ceiling.

Защитная проверка draft/final использует историческую цель и факт реально
подготовленного старого изображения, чтобы короткое «да/тест» не сбрасывало
продолжающуюся диагностику. Это отдельный внутренний контекст проверки вывода;
сводка не повышается до доверенных provider-инструкций.

Память ограничена бюджетом и может опустить деталь; точность обеспечивается
ссылками и повторным чтением оригиналов, а не обещанием безошибочного воспоминания.
История не даёт дополнительных прав, не является свежим результатом проверки
и не разрешает запись в 1С. IT по-прежнему вызывается только кнопкой и подтверждением.

Нужен scoped runtime layer поверх фактически работающего dev image; полный
branch build может затереть параллельные правки 1С/guard. Оба процесса получают
одинаковый image, прежние Compose/env/mounts/healthchecks сохраняются. APP/native
не менялись, OTA для включения памяти не требуется.

## Проверка dev-выпуска

Активный image `leaderproductapi:help-context-session-dev-20261105-r1` поверх
`help38-tabular-dev-20261105-r6`. TypeScript и 709 unit-тестов / 46 suites прошли.
11 runtime-модулей совпали по SHA-256 в API и worker. Четыре непересекающихся
1С-модуля остались byte-identical r6; удалённые phrase guards не возвращались.
Compose/env/mounts и остальные контейнеры не менялись; оба процесса healthy.

На установленном коде реальный Sol/medium восстановил раннее исправление в
синтетическом обращении из 450 сообщений, вне окна подготовки. Отдельный чат
из 150 сообщений создал приватную сводку (3 пункта, покрытие до sequence122).
В новом Node-процессе восстановлены сводка и исправленный код. Реально прочитаны
TXT/PDF/DOCX, подготовлено старое изображение, чужой messageId отклонён.
Обычный API sync не раскрыл приватную память. Редактирование оригинала сбросило
кэш. QA-обращения39/40 закрыты; уведомлений другим сотрудникам0, постоянный
тестовый аккаунт121 остался активным. Обращение38 этими тестами не изменялось.
