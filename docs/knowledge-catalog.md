# Каталог базы знаний: первая серверная версия

## Что происходит с документом

1. Редактор сохраняет файл в `V:\Leader-Product-Cloud\База знаний` через клиент Nextcloud.
2. После синхронизации worker раз в минуту обходит WebDAV. `fileid` сохраняет идентичность документа при переименовании; изменение `etag`, пути или восстановление удалённого файла создаёт новую ревизию.
3. TXT/Markdown/DOCX/PDF до 10 MiB извлекаются в дочернем процессе с ограничением времени 25 секунд и JS heap 192 MiB. Текст ограничен 500 000 символов, PDF — 500 страниц. Сканы без текста получают `NO_TEXT_OCR_REQUIRED`; OCR пока отсутствует.
4. Текст разбивается на фрагменты, индексируется PostgreSQL и получает статус `READY`.
5. По решению пользователя на dev включён `KNOWLEDGE_PUBLICATION_MODE=folder`: файл из «Материалы компании» автоматически становится доступен сотрудникам после успешной обработки. Подтверждение в админке не требуется. Папкой управляют доверенные редакторы Nextcloud. Режим `manual` остаётся значением по умолчанию для других окружений.
6. Новая версия или переименование снимают прежнюю публикацию на время обработки; новая актуальная версия включается автоматически. Перенос в архив/черновики и удаление исключают документ из ответов после успешного обхода. Ручной отзыв не отменяется автоматикой; ранее явно заданные ограничения доступа не расширяются.

`Рабочая область ИИ` извлекается для будущей проверки, но не доступна общему поиску. `Архив` и неизвестные верхние каталоги не извлекаются. Скрытые и временные файлы игнорируются. Максимум обхода: 10 000 записей и 1 000 папок; превышение фиксируется как ошибка, без массового удаления каталога.

## Права и границы пилота

- Служебный `knowledge-indexer` — не администратор Nextcloud, имеет отдельное подключение того же S3 только на чтение. У API/worker нет ключей S3 и пароля администратора Nextcloud.
- Доступ к API требует действующего пользователя-сотрудника с доступным сервисом «Помощь». Для управления нужен администратор приложения либо отдельное разрешение `manage_knowledge`; IT-роль автоматически его не получает.
- Публикация задаёт `allEmployees`, `userIds` и `departmentIds`. Администраторы/проверяющие видят каталог целиком. Для остальных сервер проверяет область доступа при каждом поиске и чтении материала.
- Это пока **явная область публикации API**, а не автоматическое отражение персональных ACL Nextcloud. До подключения разных групп редакторов требуется согласовать обе системы прав.
- Автоматический ответ Help использует только общие материалы (`allEmployees=true`), даже когда автор обращения является администратором. Ограниченные документы не копируются в обращение, доступное IT-менеджерам. Обычный защищённый поиск API продолжает учитывать персональные права.
- Изменения файлов обнаруживаются при следующем полном обходе, обычно в течение минуты после синхронизации. Это не мгновенный отзыв по событию. При ошибке источника или отсутствии успешной синхронизации более 10 минут поиск закрывается для всего источника. Ручной отзыв публикации в API действует сразу.
- Извлечение в отдельном процессе с лимитами не является полноценной OS-песочницей. Worker работает непривилегированным пользователем в контейнере с read-only filesystem, лимитом памяти и CPU. Непроверенные файлы внешних пользователей в пилот не принимаются.
- Оригиналы и история находятся в Nextcloud/S3, извлечённые ревизии и индекс — в PostgreSQL API. Срок удаления старых ревизий и текста нужно согласовать до production.

## API

Базовый путь `/knowledge`; авторизация `Authorization: Bearer <access token>`, ответы `Cache-Control: private, no-store`. Секреты не передаются через query string.

| Метод и путь | Назначение |
|---|---|
| `GET /config` | Возможности, лимиты, `canManage`; `searchMode=fulltext` |
| `GET /audience?kind=user` | Выбор получателей по именам: `kind=user/department`, `q`, `cursor`, `ids`; только проверяющему, без контактов и учётных данных |
| `GET /sources` | Состояние источника и последняя ошибка; для проверяющего |
| `POST /sources/:id/sync` | Запросить ближайший обход, тело `{}` |
| `PATCH /sources/:id` | Включить/отключить источник: `{"enabled":false}` |
| `GET /documents?view=pending&limit=30` | Каталог для проверяющего; `view=all/pending/published/processing/errors`, `section`, `status`, `q`, `cursor`, до 100 строк; удалённые скрыты, `deleted=show` включает их |
| `GET /documents/:id` | Актуальные метаданные и статус последней версии без загрузки текста |
| `GET /documents/:id/versions?before=21` | Метаданные версий по убыванию, страницы по 20; `nextBefore` для следующей страницы |
| `GET /documents/:id/versions/:revision` | Извлечённый текст выбранной ревизии для проверки |
| `GET /documents/:id/audit` | Последние 100 действий с документом |
| `POST /documents/:id/publish` | Опубликовать проверенную актуальную ревизию и область доступа |
| `POST /documents/:id/revoke` | Немедленно снять публикацию, тело `{}` |
| `POST /documents/:id/retry` | Повторить обработку текущей версии с ошибкой, тело `{}` |
| `GET /search?q=принтер&limit=10` | Найти доступные опубликованные фрагменты, максимум 20 |
| `GET /documents/:id/published` | Прочитать доступную опубликованную версию |

Пример тела публикации после просмотра текста:

```json
{
  "versionId": "UUID текущей READY-версии",
  "allEmployees": false,
  "userIds": [123],
  "departmentIds": []
}
```

Списки задаются действительными ID пользователей/отделов. Пустая область означает доступ только проверяющим. `allEmployees:true` открывает материал всем сотрудникам, допущенным к сервису «Помощь».

Ответ поиска содержит ID документа/версии/фрагмента, путь, текст фрагмента, относительный `sourceUrl` для защищённого чтения. Возвращаемый текст — обычный текст, не доверенный HTML и не инструкция для будущей модели.

## Очередь и восстановление

Задания сохраняются в PostgreSQL. `FOR UPDATE SKIP LOCKED`, уникальность задания на ревизию, lease 90 секунд и случайный fencing token не дают прежнему worker записать результат после перехвата задания. Временные ошибки повторяются с задержкой, не более пяти попыток; постоянные ошибки требуют исправления/повтора. После скачивания используется условный GET по ETag, после извлечения повторно проверяются fileid/etag, а перед записью — текущая ревизия и lease в транзакции.

Удаление отсутствующих файлов выполняется только после успешного полного обхода. Частичный ответ WebDAV, потеря доступа, лимит обхода или ошибка сети не трактуются как удаление всех документов. Перезапуск worker не обнуляет очередь.

`KnowledgeSource.lastErrorCode`, возраст `lastSuccessAt`, состояния очереди и ошибки ревизий показывают состояние данных. Docker healthcheck контролирует продвижение цикла worker; отдельно требуется наблюдение за ошибкой источника и возрастом очереди.

## Конфигурация и запуск

Пример без секретов есть в `.env.example`. `KNOWLEDGE_ENABLED=false` по умолчанию. Включение требует `KNOWLEDGE_SOURCE_KEY`, HTTPS-origin `KNOWLEDGE_NEXTCLOUD_URL`, пользователя, пароля или `KNOWLEDGE_NEXTCLOUD_PASSWORD_FILE`, корня `KNOWLEDGE_NEXTCLOUD_ROOT` и `DATABASE_URL`.

```bash
npm run prisma:generate
npm run build
npm run worker:knowledge
```

Переменные передаются окружением/приватным env-файлом; значения `.env.knowledge.worker.local` не загружаются автоматически. При `worker:knowledge:dev` также нужна предварительная сборка: дочерний парсер запускает скомпилированный JS.

Для существующего dev применяется **только** миграция `20261031150000_knowledge_catalog` через `scripts/apply-knowledge-migration.cjs`, с `KNOWLEDGE_MIGRATION_TARGET=dev`, `KNOWLEDGE_MIGRATION_DATABASE_CONFIRM=LeaderAPI_dev`, `DB_ACCEPT_DATA_LOSS=0`. Сначала обязательна проверенная резервная копия. Скрипт использует существующий журнал `HelpSchemaVersion`, проверяет checksum и отказывается менять частично существующую схему. `db push` на dev/prod не применяется. Для production нужен отдельный согласованный выпуск и обычный migration baseline.

Compose overlay: `deploy/knowledge/compose.worker-dev.yml`, поверх действующей конфигурации API/Help. Worker ограничен 512 MiB, 0.5 CPU, 64 PID; наружных портов нет. API получает те же параметры источника. Не пересоздавать PostgreSQL/Redis/Help worker при выпуске этой части.

## Проверено и что остаётся

На отдельной БД проверены обнаружение, идемпотентность обхода, публикация/отзыв, запрет недоступных документов, скрытие черновиков/архива, недоступность устаревшего источника, смена версии в процессе извлечения, перехват истёкшего lease, переименование и удаление. Реальные парсеры обработали синтетические TXT/MD/DOCX/PDF; повреждённый PDF отвергнут. Миграция применена и повторно проверена, схема совпала с Prisma. Семь unit-проверок WebDAV/ограничений/разбиения прошли.
