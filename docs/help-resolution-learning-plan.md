# Пополнение базы знаний после закрытия обращения

Дата: 01.11.2026. Статус: план реализации; новый обработчик и таблицы пока не созданы.

## Результат для пользователя

После закрытия обращения серверный ИИ через некоторое время разбирает переписку и подтверждённое решение. Он определяет, нужно ли создать инструкцию, дополнить существующую, предложить её переработку или ничего не менять. Работа продолжается на VDS при закрытом приложении и выключенном компьютере разработчика.

Результат появляется файлами в существующей папке `База знаний/Рабочая область ИИ`. Ответственный сотрудник проверяет предложение через Nextcloud/Проводник. Развитие отдельного интерфейса админки для этого не требуется.

## 1. Отложенное задание

1. В транзакции закрытия обращения сохранить событие закрытия и `HelpKnowledgeReviewJob`. Очередь долговечная в PostgreSQL, локальные таймеры приложения не используются.
2. Начальная предлагаемая задержка — **30 минут**, настраивается через `HELP_KNOWLEDGE_REVIEW_DELAY_MINUTES`. Это стартовое предложение, а не уже установленная настройка. Обрабатывать и обращения, решённые IT, и подтверждённые решения помощника.
3. Уникальность задания: `(ticketId, closureEventId)`. Сохранить номер последнего события/сообщения и версию входного материала. Повтор доставки события не создаёт дубликат.
4. Повторное открытие отменяет ожидающее/выполняющееся задание. Новое сообщение или уточнение решения делает старый снимок неактуальным; для остающегося закрытым обращения пересобрать снимок и отложить запуск. Новое закрытие создаёт новое задание.
5. Перед анализом и перед сохранением результата проверить, что обращение всё ещё закрыто, событие закрытия и ревизия совпадают. Устаревшее предложение не выдавать за актуальное.
6. Worker использует lease, fencing token, ограниченные повторы, backoff и возобновление после перезапуска. Внешний вызов OpenAI не удерживает транзакцию БД. Логи содержат ID/этапы/коды ошибок, а не пароли и полную переписку.

Существующий механизм `HelpAssistantJob` служит образцом гарантий выполнения. Отдельный тип задания нужен, чтобы разбор закрытых обращений не создавал лишнее сообщение в чате и не конкурировал с текущими ответами за приоритет.

## 2. Основания для инструкции

Входные данные: симптомы, контекст и версии систем, сообщения о проверках, действия IT, результат, подтверждение решения, связанные источники и их версии. Неудачные советы не превращаются в рекомендуемые действия.

Закрытие, оценка или уверенный текст ИИ сами по себе не доказывают устранение проблемы. Если переписка не содержит подтверждённого решения, сохранить причину `needs_review`/`no_change`, не выдумывать инструкцию. Вложения обрабатывать только через разрешённые извлекатели; не считать непроверенный OCR установленным фактом.

Рабочие проверки 1С при необходимости выполняются с VDS через разрешённые инструменты. Текущее состояние системы спустя 30 минут не подменяет доказательство причины прошлой неисправности.

## 3. Решение о документе

| Решение | Когда применяется | Результат |
|---|---|---|
| `no_change` | Существующая инструкция достаточна; нового подтверждённого знания нет | Краткий разбор со ссылкой на документ |
| `create` | Подтверждённое решение нового повторяемого случая | Новая инструкция-черновик |
| `update` | У статьи не хватает шага, условия, варианта ошибки | Предложение изменений с diff |
| `rewrite` | Статья устарела/противоречива и точечной правки недостаточно | Новая редакция, diff и обоснование |
| `needs_review` | Нет уверенного соответствия, противоречивые результаты или доступ | Разбор для специалиста, без автопубликации |

Перед генерацией искать похожие инструкции, существующие кандидаты и разборы по теме. Сравнивать проблему, область применимости и решение; одного похожего заголовка недостаточно. Сохранять найденный документ, его ревизию/хеш и причину выбора. Повторные похожие обращения дополняют существующее предложение, а не размножают копии.

## 4. Файлы и публикация

Использовать уже созданные каталоги:

```text
База знаний/
  Материалы компании/                    # Только проверенные материалы для ответов
  Рабочая область ИИ/
    Разборы обращений/                   # Краткий очищенный итог и принятое решение
    Черновики инструкций/                # Подготовка новой инструкции/редакции
    На проверке/<candidateId>/
      Инструкция.md                     # Предлагаемая новая редакция
      Изменения.patch                   # Для update/rewrite
      Сведения.json                     # ID источников, базовая версия, причина
  Архив/                                # Выведенные из использования материалы
```

Имена файлов — предлагаемый контракт нового обработчика, ещё не реализация. Для `no_change`/`needs_review` создавать только подходящий разбор, без пустой инструкции. Человекочитаемое имя может содержать тему и номер обращения; ID кандидата стабилен при повторах.

ИИ **не перезаписывает `Материалы компании` самостоятельно**. В существующем режиме `folder` файл в этом каталоге после успешной индексации становится источником для ответов. Поэтому автоматический анализ и публикация должны оставаться разделены.

Редактор проверяет решение, область доступа, ссылки на доказательства и diff. Затем размещает подтверждённую редакцию в нужном разделе `Материалы компании`, следуя текущему файловому процессу. Предыдущую опубликованную версию сохранять согласно правилам истории/архива. При переносе сначала обеспечить готовность новой версии, чтобы не потерять рабочую инструкцию из поиска.

Обновление связывать с `documentId` и конкретной базовой версией/ETag/хешем. Если документ успел измениться, статус `conflict`: автоматически не затирать редакторские изменения. После индексации подтверждать связь кандидата с опубликованным `KnowledgeVersion`; перемещение файла само по себе не доказывает корректность публикации. Смена прав/отзыв документа повторно проверяются перед подготовкой и публикацией.

## 5. Доступ и очистка данных

- Отдельная служебная учётная запись Nextcloud пишет только в `Рабочая область ИИ`. Существующий `knowledge-indexer` остаётся на чтение. Секрет учётной записи хранится на VDS с ограниченными правами, не на компьютере разработчика.
- Рабочая область ИИ доступна проверяющим специалистам, не всем сотрудникам. Из закрытых/ограниченных обращений нельзя автоматически делать общедоступные статьи.
- Удалять пароли, API-ключи, SSH-ключи, токены, персональные и клиентские сведения, не нужные инструкции. Очистка выполняется до передачи внешней модели; последующая проверка результата — второй барьер.
- В файле сохранять безопасные ссылки на доказательства; полная переписка остаётся в API с исходными правами. Доступ к разбору не должен расширять права на источник.
- Права целевой статьи не шире допустимых для материала. При неясной области доступа — `needs_review`.
- Сообщения и документы не могут давать worker новые полномочия. Никаких произвольных shell/SQL-команд по тексту переписки.

## 6. Данные и согласование состояний

Предлагаемые сущности:

- `HelpResolution`: подтверждённое решение, кем и когда подтверждено, доказательства, событие закрытия.
- `HelpKnowledgeReviewJob`: статус, `notBefore`, ревизия входа, attempts, lease/fencing, отмена/ошибка.
- `KnowledgeCandidate`: тип решения, текст/diff, целевой документ и версия, статус проверки, область доступа, история решений редактора, publishedVersionId.
- Связь кандидатов с несколькими обращениями и точными сообщениями, без копирования лишних персональных данных.

Запись в БД и WebDAV не атомарны. Сначала сохранять кандидат и задание экспорта в БД, затем идемпотентно создавать/обновлять файл по стабильному ID с контролем ETag. Отдельная сверка восстанавливает незавершённые выгрузки; повтор не создаёт новую копию. Не затирать файл, который редактор уже изменил.

Повторное открытие обращения помечает связанный кандидат как требующий пересмотра. Если статья уже опубликована, создать сигнал проверки с объяснением; не удалять автоматически весь материал по одному повторному обращению.

## 7. Этапы реализации

- [ ] Миграция сущностей, событие закрытия и долговечное отложенное задание; включение флагом `HELP_KNOWLEDGE_REVIEW_ENABLED` (по умолчанию выключено).
- [ ] Worker со снимком данных, lease/fencing, отменой при повторном открытии/новых сообщениях, метриками возраста очереди и причин отказа.
- [ ] Проверка достаточности решения, очистка данных, поиск дубликатов и выбор create/update/rewrite/no_change/needs_review.
- [ ] Структурированный ответ через существующий адаптер OpenAI; отдельные промпт/схема, лимиты и бюджет фонового анализа. До получения ключа проверять контракт фиксированными ответами, не выдавать симуляцию за настоящее обучение.
- [ ] Ограниченная учётная запись WebDAV, идемпотентная выгрузка кандидатов, защита изменений редактора и контроль публикации новой версии.
- [ ] Пилот на обезличенных закрытых обращениях: сравнить с решением IT, затем разрешить создание черновиков рабочих случаев.

Проверки только нового сценария: подтверждённое решение; отсутствие решения; повторное открытие до/во время анализа; новое сообщение; повтор события; падение worker; дубликат инструкции; конфликт редакций; удаление/отзыв источника; секреты/ограниченные данные; сбой WebDAV после записи БД; успешная публикация и использование следующей версией поиска.

Критерий готовности: закрытое обращение после заданной задержки обрабатывается на VDS, даёт обоснованный кандидат либо no_change; не теряется при перезапуске; не изменяет опубликованную инструкцию без проверки; одобренная версия становится доступна следующему похожему обращению с сохранённым происхождением.
