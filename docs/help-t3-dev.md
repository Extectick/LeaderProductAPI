## Обмен и границы

Действующий PostgreSQL HelpAssistantJob остаётся владельцем задания. Worker
вызывает провайдер `t3` под существующей продлеваемой арендой. В Redis создаётся
временный запрос (TTL 360 секунд), адресуемый случайным UUID, с SHA-256 временной
256-битной capability. В webhook отправляются только version/requestId/capability,
без переписки, источников, employee JWT, паролей 1С и инфраструктурных секретов.

Агент T3 использует helper `scripts/bridge.mjs`, который умеет только:

- GET `https://dev.lidprod.ru/help/t3/requests/:id` — получить контекст;
- POST `https://dev.lidprod.ru/help/t3/requests/:id/result` — вернуть
  `{decision: answer|clarify|handoff, message, source_ids}`.

Capability передаётся через Authorization, а не URL. Helper не принимает адрес API
из webhook, не следует редиректам и ограничивает размер входа/ответа. Роуты API
смонтированы до JSON/debug/Kafka логирования и JWT middleware; имеют собственную
проверку capability и ограниченный parser, без записи тела/секретов в глобальные логи.
Выключенный провайдер возвращает 404, не обращаясь к Redis/БД.

При получении контекста и результата проверяются актуальная аренда, provider,
ticket/owner, статус обращения, отсутствие IT и права владельца/источников.
Первый валидный результат сохраняется через NX, повторы получают 409. Worker
повторно проверяет права и аренду в обычной транзакции завершения Help. Поздний
ответ после отмены, нового сообщения, передачи IT или перезапуска worker не может
заменить актуальный. Переключение между T3 и Bunny блокирует ответ старого провайдера.
При остановке worker исходное PostgreSQL-задание сохраняется; новый worker создаёт
новую временную capability. Обмен очищается при завершении/ошибке и имеет TTL.

Текст истории ограничен 6000 символами/16 сообщениями, источники — 3 документами
и 9500 символами. Вложения, URL файлов, персональные 1С-инструменты и действия
изменения данных не предоставляются. Если KNOWLEDGE_ENABLED выключен, разрешена
общая помощь без утверждений о компании; если включён — действует существующая
политика retrieval/handoff, без внешнего запроса при недоступных знаниях.
Явный dev-флаг `HELP_T3_ALLOW_GENERAL=true` разрешает общую диагностику при
отсутствии подходящих инструкций (`no_knowledge`). Он не отключает каталог знаний,
проверку источников, обработку недоступного хранилища или запрос передачи IT.
Без источников помощник не должен придумывать факты о компании.

Отмена блокирует доступ и доставку результата, но не гарантирует остановку самого
процесса агента в T3. Контекст может сохраняться в истории T3; доступ к проекту и
срок хранения нужно определить при активации. Максимум ожидания ответа — 5 минут,
максимум попыток — 2. Метаданные модели помечены `t3-configured-provider`, usage
не выдумывается. Модель определяется настройками T3, не ключом в мобильном APP.

## Повторное развёртывание и откат

1. Убедиться, что выбранный провайдер модели в T3 допускает запланированное
   серверное использование. Сам T3 не меняет условий авторизации/лимитов модели.
2. Включить remote access T3 Connect. Получить webhookUrl выключенного задания;
   сохранить его приватно, без вывода в чат/логи, как секрет. Не угадывать URL.
3. Проверить настройки модели и режим запуска в отдельном проекте, фиксированный
   адрес helper и доступ до `https://dev.lidprod.ru`. Webhook пока оставить выключенным.
4. Выпустить подготовленный код API/worker в dev с прежним Bunny. Новый адаптер
   выключен по умолчанию. Не применять `.env` из handoff и не менять production.
5. На docker-01 под `/opt/leader-api-dev/deployment.lock` сохранить фактическую
   разрешённую Compose-конфигурацию и старые provider flags в приватный backup.
   Сверить host, `NODE_ENV=development`, базу `LeaderAPI_dev`, защиту от потери данных,
   одинаковый выпущенный образ API/worker и схему Help без миграций.
6. Скопировать `deploy/help-t3.dev.example.json` в приватный
   `/opt/leader-api-dev/help-t3.private.json` (0600), сохранить реальный URL в
   `/opt/leader-api-dev/secrets/help-t3-webhook-url` (0600). Проверить, что файл
   читается пользователем контейнера. Пример — overlay для уже настроенного Help
   worker, он не создаёт его image/command/env_file/networks с нуля.
7. Итоговый порядок Compose: существующий base + прежний Bunny binding + T3 binding
   + release-image. Сверить **всю** итоговую конфигурацию с живыми сервисами; менять
   только API и Help worker, сохраняя знания, env, сеть и volumes. Шаблон очищает
   inline Bunny/OpenAI keys для этих процессов; старый Bunny binding остаётся для
   отката. Если секреты смонтированы иным способом, отдельно убрать их из T3 runtime.
8. Включить созданный webhook, затем применить оба сервиса с opt-in:
   `HELP_AI_ENABLED=true`, `HELP_AI_PROVIDER=t3`, `HELP_T3_DEV_ENABLED=true`,
   `HELP_T3_WEBHOOK_URL_FILE=/run/secrets/help_t3_webhook_url`.
9. Проверить через отдельное тестовое обращение ответ, повторный вопрос,
   отмену/новое сообщение, недоступный webhook, восстановление worker и передачу IT.
   Убедиться, что публикуется ровно один результат и уведомление, а посторонние
   контейнеры/данные не изменились. Не использовать рабочую переписку для пробы.

`scripts/deploy-server-api.py` подготовлен к сохранению T3 binding при следующих
dev-релизах: T3 применяется после Bunny, оба сервиса обновляются одним образом.
Наличие файла ничего не включает в работающем процессе без явного применения.
Production игнорирует оба dev binding. Другие старые server provisioning helpers
могут не знать T3: не запускать их поверх активированного binding без сверки.

## Откат

Выключить webhook; под тем же deployment lock убрать T3 overlay из применяемого
набора и восстановить сохранённую конфигурацию API/worker с Bunny. Не менять БД,
не чистить HelpAssistantJob, переписку, очереди и историю APP. Выключенные T3 endpoints
возвращают 404; поздние callbacks отвергаются. Убедиться, что следующий image-only
release не подхватит оставленный `help-t3.private.json`: перенести файл в приватный
backup. Проверить Bunny на отдельном тестовом обращении.
