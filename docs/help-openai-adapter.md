## Выполнение задач и диагностика 1С — 10 ноября 2026

Dev API и worker: `leaderproductapi:help-task-execution-dev-20261110-r1`,
точечный слой над `help-voice-mail-dev-20261108-r1`. Девять существующих runtime
модулей изменены, три добавлены, 1277 сохранены; все 1289 файлов сверены.
Основная модель остаётся Sol/medium. `HELP_OPENAI_TIMEOUT_MS=300000` установлен
в обоих private OpenAI bindings; бюджет инструментов по умолчанию48, допустимый

Lease heartbeat, отмена, личные права, запрет записи в1С и генерации медиа сохранены.

Строгий ответ провайдера теперь содержит краткий `task` (цель, вид, статус,
недостающий результат). `continue` продолжает инструменты внутри задания, а перед
итогом поиска/действия выполняется внутренняя проверка соответствия цели. Живой
выбор и завершение больше не зависят от `requiresOnecRead/BusinessRead` и списка
слов о товарах/складах. Модельный self-check не является доказательством точности.

`onec_recall_metadata` восстанавливает изученные в этом обращении структуры одним
вызовом (до8 за порцию): предыдущие успешные задания дают только валидированные
селекторы, сами структуры заново читаются через текущую личную учётную запись.
Исторические бизнес-строки не выдаются за свежие. Авторизация проверяется до
публикации; смена подключения не позволяет прочитать старый результат в обход прав.
Обычный диалог не инициирует фоновое чтение1С ради восстановления метаданных.

Ошибки запросов1С различаются по серверным кодам причины и числовой позиции.
Исходные ошибки, запросы и секреты не возвращаются в диагностике. В частности,
псевдоним `В` приводил к «Ожидается имя»; точная диагностика позволяет модели
исправить запрос. При слишком большом ответе чтение повторяется с меньшей порцией
без изменения условий/параметров, с тем же таймаутом и явным `truncated`.
Порция не ограничивает исходную совокупность для агрегатов.

Фильтр больше не отвергает рекомендации только из-за запуска PowerShell с
правами администратора. Инструкция требует основания, объяснения области действия,
последствий и отмены; это не выдаёт пользователю права и не исполняет команды.
Шлюз имеет новые фиксированные read-only операции `dhcp/devices/printers/smb`;
подробности и ограничения — `deploy/help-gateways/README.md`.

Проверки:439 API unit-тестов,12 Python-тестов, TypeScript; реальные Sol проверки
продолжения и восстановления метаданных; авторизованные запросы1С и новые
диагностики через действующий API. Тесты не меняли обращения или бизнес-данные.
История версий сама по себе не устанавливает автора пометки удаления: если

## Постоянные расшифровки голосовых — 8 ноября 2026

`help.ai-audio.ts` распознаёт только голосовые из новых входных сообщений текущего
задания (включая несколько сообщений, отправленных подряд до ответа). История
получает уже сохранённые расшифровки без повторного обращения к speech API.
При работе IT отдельная фоновая очередь распознавания не запускается: пользователь
может распознать запись кнопкой. Старое аудио также доступно по явному запросу
инструменту `help_read_attachment`.

`HelpAudioTranscript` хранит успешный текст или результат «речь не распознана»
без срока истечения, на весь срок жизни вложения. Удаление вложения удаляет запись
через внешний ключ. Перезапуск API/worker, смена модели и повторный запрос не
запускают распознавание заново для неизменившегося вложения. История сообщений
не переписывается; текст остаётся содержимым исходного автора, а не инструкцией.

API и worker используют одну атомарную запись-аренду PostgreSQL, поэтому одновременные
запросы кнопки и ИИ не запускают два распознавания. Результат сохраняется до подготовки
контекстного окна. Завершённый результат не имеет TTL; только незавершённая аренда
истекает через 180 секунд для восстановления после аварии процесса. Ошибку можно
повторить явно; при неопределённом сетевом исходе гарантировать ровно один платный
вызов внешнего провайдера невозможно.

Авторизация сервиса, обращения, автора и привязки аудио проверяется при чтении
готового текста и при распознавании. История и исходный SHA/размер/MIME повторно
проверяются до публикации результата. IT использует обычные права просмотра Help.
Ключ OpenAI и прокси остаются серверными. Основная модель/права 1С не меняются.

`GET /help/attachments/:id/transcript` читает состояние без запуска распознавания.
`POST` по тому же адресу с `{}` запускает или повторно использует результат;
если запись уже обрабатывается другим процессом, ответ 202 `pending`.
Обычный ответ 200: `{attachmentId,status,text?,truncated?,reason?}`, статусы:
`not_started`, `pending`, `transcribed`, `no_speech`, `unavailable`.
Первый POST может ждать до 90 секунд; клиенту нужен таймаут 120 секунд. После
запуска закрытие экрана не отменяет распознавание: сервер завершает и сохраняет
его в пределах независимого срока 110 секунд, повторно проверяя доступ и источник. Ошибки
провайдера не передаются пользователю. GET не восстанавливает просроченную аренду;
явный POST может повторить неудачную операцию.

Один файл до 20 МиБ; до 32000 символов с явной отметкой усечения. Поддержаны
M4A/MP4, WEBM, MP3, WAV, OGG и FLAC. Автоматический бюджет новых входных записей
120 секунд; старые записи из него не отправляются на распознавание.

Перед dev rollout применить только
`HELP_MIGRATION_TARGET=dev DB_ACCEPT_DATA_LOSS=0 HELP_MIGRATION_DATABASE_CONFIRM=LeaderAPI_dev node scripts/apply-help-audio-transcripts.cjs`
в существующем защищённом окружении dev API. Скрипт проверяет базу, checksum,
структуру и FK, атомарно создаёт единственную таблицу и запись HelpSchemaVersion.
Не запускать все исторические миграции. Runtime использует параметризованный SQL,
обновление сгенерированного Prisma Client для этого слоя не требуется.

Контракт speech: [официальная документация OpenAI](https://developers.openai.com/api/docs/guides/speech-to-text).
Проверки: `help.ai-audio.unit.test.ts`, `help.audio-transcript.unit.test.ts`,
`help.openai-grounding.unit.test.ts`. Реальные голоса/тексты не писать в логи.

Каждый запуск Help получает короткий серверный `requester`: APP id владельца
обращения, отображаемое имя, роль, тип профиля и готовую ссылку на его карточку.

профиль. Контакты, пароли и реквизиты 1С не выбираются. Для «пришли мой профиль»
не нужны ФИО, поиск сотрудников и чтение 1С. Прежние ошибочные ответы в истории
не заменяют актуальную идентичность владельца.

`help.requester-context.ts` привязывает контекст только к серверному `ownerId`.
Идентичность проверяется перед передачей модели, при продолжении потока и внутри
существующих транзакций публикации. Отключение/блокировка/удаление пользователя
или изменение выбранных полей останавливают публикацию устаревшего ответа.
Роль в контексте не выдаёт прав: проверки инструментов, личной 1С, источников,
lease и состояния обращения остаются обязательными. Контекст и функции проверок

личный binding/revision и явно отмечает неполные структуры. Метаданные и права
сами по себе не считаются доказательством наличия/отсутствия деловых данных.

Пустой результат, отсутствие склада или метаданных возвращаются агенту для
дальнейшей проверки. После неудачного буквального поиска разрешено уточнить
фрагмент; исходная опечатка больше не подменяет все последующие попытки.
Ранний IT-handoff после успешно полученных метаданных удерживается внутри
проверки, если ещё доступны инструменты и не было ошибки. Настоящие неоднозначные
варианты по-прежнему предлагаются сотруднику для выбора, без назначения по умолчанию.

вопросы из 100 последних реплик. Это слова сотрудника, не подтверждённые данные
или полномочия; новые темы не должны наследовать старые условия автоматически.

Это уменьшает возможности внедрённых инструкций, но не заменяет проверку качества ответов реальной модели.
- `store:false`, собственная история в PostgreSQL; удалённая цепочка `previous_response_id` не используется. Это отключает хранение Responses для последующего получения, **но не является обещанием Zero Data Retention**: условия обработки данных аккаунта нужно проверить до включения.
- Проверка актуальности и доступности источников до передачи провайдеру и перед сохранением ответа. При отзыве/изменении во время запроса результат не сохраняется, задание готовит ответ заново. Уже отправленные провайдеру данные нельзя отозвать задним числом.
- Без документов и инструментов 1С обращение обычно передаётся в IT без платного запроса. В dev явный `HELP_OPENAI_ALLOW_GENERAL=true` разрешает общую диагностику при `no_knowledge`, с недавней историей текущего обращения. Флаг не действует в production/test, не разрешает выдумывать факты компании и не отменяет передачу IT по запросу пользователя или при недоступности источников. С включёнными инструментами модель может проверить 1С; отсутствие личного доступа возвращает кнопку подключения. Отказ модели и решение `handoff` ведут в IT. `clarify` сохраняется как вопрос в текущем чате.
- В успешном ответе сохраняются модель, ID ответа и usage, суммарный по всем раундам инструментов, включая `reasoningTokens`, если API их сообщил. Зашифрованные reasoning items передаются в следующий раунд инструментов при `store:false`; внутренние рассуждения не выводятся пользователю. Socket-событие и запись в outbox создаются той же транзакцией, что финальное сообщение.

### VPN и повторный выпуск dev

Порядок Compose: `compose.yml`, прежние Bunny/T3 binding при наличии, `help-openai.private.json`, `release-image.json`. Последний provider binding выбирает OpenAI; прежняя конфигурация T3 сохранена для отката. `scripts/deploy-server-api.py` сохраняет этот порядок только для dev. Ключ — `/opt/leader-api-dev/secrets/help-openai-api-key`, UID 10001, 0400.

Отдельный Supervisor program `leader-help-openai-vpn` в workspace принимает только CONNECT к `api.openai.com:443` через приватный Unix socket и передаёт его действующему VPN-прокси `127.0.0.1:10809`. Dev sidecar `leader_help_openai_vpn_dev` доставляет TCP до этого socket через read-only mount каталога из homes volume. У sidecar нет ключа OpenAI и опубликованных портов. TLS до OpenAI проверяется обычным образом. Глобальный proxy, T3, Metro, firewall, production и другие контейнеры не меняются.

Код шлюза: `deploy/help-openai-vpn-proxy.cjs`; проверка: `node --test scripts/test_help_openai_vpn_proxy.cjs`. Неверный destination получает 403; при недоступности VPN прямого fallback нет. `HELP_OPENAI_PROXY_URL` применяется только к вызовам Help OpenAI, а не к знаниям, БД или 1С. После reboot требуется рабочий workspace, его homes volume и VPN; Supervisor и restart policy sidecar восстанавливают процессы. Socket после аварийного завершения заменяется только после проверки отсутствия слушателя.

API и worker должны проходить runtime healthcheck; в overlay явно выставлен `healthcheck.disable=false`, иначе старый Compose worker сохраняет отключённую проверку. Для будущего образа нужна зависимость `undici` 7.x, актуальные OpenAI и T3 adapters, Redis bootstrap. Миграций для переключения не требуется. Приватный rollback snapshot: `/opt/leader-api-dev/backups/openai-enable-20261104T162432Z/`. Для отката восстановить provider/image и оба процесса; БД и переписку не восстанавливать поверх новых данных.

## Отмена, повторы и ограничения

Запрос выполняется вне транзакции БД. Пока он идёт, worker раз в две секунды проверяет владение заданием и продлевает действующий lease на 90 секунд. Уточнение пользователя, отмена или подключение IT прерывают HTTP-запрос. Перед финальной записью сохраняется проверка токена владения: прежний исполнитель не может опубликовать ответ.

Остановка worker прерывает запрос и возвращает ещё принадлежащее ему задание в очередь. Завершение локального HTTP-запроса не гарантирует остановку вычисления у провайдера. После сбоя между получением ответа и фиксацией в БД возможен повторный платный вызов; ровно один внешний вызов не гарантируется. Финальное сообщение/событие защищены от дублей.

HTTP 408/429/5xx, сетевые сбои и таймауты повторяются через существующую очередь. Учитывается `Retry-After` до пяти минут. Ошибки конфигурации, авторизации, JSON и вымышленные ссылки не повторяются автоматически. Тело ошибки провайдера не сохраняется и не выводится в лог.

Пределы: таймаут 1–300 секунд, выход 128–4 000 токенов, 1–5 попыток. Значения по умолчанию — 60 секунд / 1 500 токенов / 3 попытки; активный dev использует 4 000 токенов и 2 попытки. Выходной бюджет включает reasoning tokens. Это ограничение отдельного задания, **не общий суточный денежный бюджет**. Учёт всех платных попыток и глобальные квоты остаются отдельным этапом перед масштабированием. Живым тестом проверены ключ, выбранная модель и основной путь ответа; полноценная оценка качества, всех инструментов 1С и затрат на серии обращений ещё требуется.

## Статистика пользователей приложения (обращение46)

`app_get_user_stats` читает один агрегат по `User.isActive`, исключая `deletedAt != null`.
Возвращает `total`, `enabled`, `disabled`, `asOf` и явную область
`non_deleted_accounts`. Включённая учётная запись не означает пользователя онлайн
или активность за период. Имена, ID пользователей, контакты, логины и секреты
в результат инструмента не включаются; сам инструмент не принимает фильтры/SQL.

Доступ совпадает с `/users/admin/list`: административная роль в глобальной цепочке
либо `manage_users` через глобальную/отдельскую роль и их родителей. Само наличие
профиля сотрудника или права `manage_help` не даёт статистику. Аккаунт запрашивающего
должен быть активным, не удалённым/заблокированным; блокировка профиля сотрудника
также запрещает запрос. Права проверяются до и после чтения, перед дальнейшей
передачей модели, внутри каждой транзакции сохранения публичного прогресса и
перед финальной публикацией. Отзыв доступа останавливает публикацию без повторов.

Для прямого вопроса о количестве пользователей приложения первый вызов закреплён
за этим инструментом. Поиск профилей, старые ответы и инструкции не заменяют свежий
агрегат. `APP_USER_STATS_FORBIDDEN` означает отказ по правам, а не нулевое количество;
модель предлагает помощь администратора без обращения к 1С и без изменения прав.
Передача в IT по-прежнему требует пользовательской кнопки и подтверждения.

число, а ответ без источника останавливался `HELP_OPENAI_INVALID_CITATIONS`.
Проверка источников сохранена. Непроверенные счётчики завершаются отдельным
`HELP_APP_STATS_UNVERIFIED`; до успешного чтения их черновики не показываются.

отзыв во время запроса, прогресса и финальной транзакции, нулевой результат и
